## Findings

### [P1] Flash messages render success-green even when they report a failure
**Location:** `console/console.go:325-327, 591`; `onboarding.html:23`
**Category:** Accessibility / Error recovery
**Impact:** 25 `flashRedirect` calls share one channel, and at least one carries
a rejection (`"Policy rejected: " + err`). `.flash` is styled with success
tokens, so a failed operation is announced in green. `.flash-error` exists in
CSS but nothing can reach it. A user who mistypes a Cedar policy is told, in the
visual language of success, that it failed.
**WCAG:** 1.4.1 Use of Colour (compounded: colour says the opposite of the text)
**Recommendation:** Give `flashRedirect` a severity, emit `flash flash-error`
for failures. The CSS is already there.
**Command:** `/impeccable harden`

### [P1] Five interactive targets below the 24px WCAG 2.5.8 minimum
**Location:** breadcrumb links on `agent.html`, `session.html`, `eval-run.html`
(44x16, 44x16, 147x16); rate inputs on `onboarding.html` (291x21, 49x21)
**Category:** Accessibility / Responsive
**Impact:** Fails the AA target-size floor. The breadcrumb is the only in-page
back navigation on those three pages, so the smallest target is also the one a
lost user reaches for.
**WCAG:** 2.5.8 Target Size (Minimum), Level AA
**Recommendation:** `padding-block: .35rem` on `.breadcrumb a`; raise input
padding so the rate fields clear 24px.
**Command:** `/impeccable adapt`

### [P2] Required fields carry no visible indicator
**Location:** `onboarding.html` — 11 `required` attributes, 0 visual marks
**Impact:** The browser only reveals a required field on submit. In a 39-input
page, the user discovers the requirement by failing.
**WCAG:** 3.3.2 Labels or Instructions
**Command:** `/impeccable harden`

### [P2] No client-side validation on the JSON and Cedar textareas
**Location:** `onboarding.html:267, 324, 356`
**Impact:** A malformed JSON eval set round-trips to the server to fail. Zero
`pattern`/`oninvalid` handlers.
**Command:** `/impeccable harden`

### [P2] 66 of 69 onboarding targets are under 44px
**Location:** all `.row` form controls
**Impact:** Above the 24px AA floor, so not a violation, but below the iOS/AAA
comfort guidance. Defensible for a desktop operator tool; worth being a decision
rather than an accident.
**Command:** `/impeccable adapt`

### [P3] `.subtitle` still serves four unrelated roles
Page subtitle, panel description, table timestamp, inline agent name. The
eval-run error was moved off it, which was the harmful case.

### [P3] No `<meta name="description">` or favicon
Browser tabs show a generic globe.

### [P3] Onboarding has no auto-refresh for in-flight state
A `running` eval run shows `—` until manual reload.

## Patterns and Systemic Issues

1. **The error path is the thin one.** Both P1s and both validation P2s are the
   same shape: the success path is carefully built, the failure path inherits
   whatever the success path had. Same root as the critique's heuristic-9 score.
2. **Density was chosen deliberately; target size was not.** Compact controls
   are correct for this tool. But 5 elements fell under the AA floor by
   accident, not by decision.

## Positive Findings

- **Theming is finished work.** 149 token references; the only hard-coded values
  are three Google brand colours, documented with the reason they are exempt.
- **Air-gap claim verified.** Zero external subresources across all nine
  templates. 26KB CSS, 3KB JS, no fonts, no CDN. The constraint in PRODUCT.md is
  real, not aspirational.
- **Keyboard navigation is clean.** No positive `tabindex`, no traps, focus
  indicators on all five interactive element types, skip link first in tab order.
- **Semantics are correct.** No heading-level skips, one `h1` per page, real
  `header`/`nav`/`main` landmarks, zero `div[onclick]`, all 9 tables use `th`.
- **Contrast passes everywhere.** 281 text nodes across nine pages, zero
  failures, measured against real computed backgrounds.
